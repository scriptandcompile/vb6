Overview

vb6format transforms VB6 source code through a multi-pass formatting pipeline. Rather than applying all formatting rules in a single traversal, the formatter delegates responsibility to six specialized passes, each handling one aspect of formatting: line endings, compiler directives, keyword casing, layout (indentation and whitespace), top-level spacing, and blank line deduplication.

This design mirrors the pipeline model used by modern formatters like Rustfmt and Black, but is tailored to the unique structural challenges of VB6: hybrid .frm files with designer blocks, compiler directives that affect indentation, compound keywords like End If, and the need to preserve the VB6 IDE's opaque property blocks verbatim.

Core principle: Each pass is independent and stateless except for shared context. This makes the pipeline easy to extend, reorder, or disable without affecting other passes.

Why Multi-Pass?

A single-pass formatter would need to interleave all formatting logic, making it difficult to reason about, test, or modify individual rules. The multi-pass approach separates concerns cleanly:

✅ Multi-Pass
  • Single responsibility: Each pass does one thing well
  • Testable: Pass behavior is isolated and verifiable
  • Composable: Passes share context; they compose modifications to a single token buffer
  • Configurable: Passes can be enabled/disabled via FmtSettings
  • Extensible: New passes can be added by inserting into the pipeline order
⚠️ Trade-offs
  • Multiple traversals over the token stream (mitigated by the small constant of 6 passes)
  • Shared context state must be carefully managed
  • Pass order matters and must be documented

In practice, the performance cost is negligible. The pipeline processes tokens sequentially through all six passes per token — a constant factor of 6× — but each pass is a simple state machine with no backtracking or expensive data structures. The alternative of a monolithic formatter would be materially more complex with no meaningful performance gain.

The Pipeline

The formatter applies six passes in a fixed order. Each pass receives the same Context and modifies the same TokenBuffer, allowing modifications to compose naturally:

CST (Concrete Syntax Tree)
(parsed from source by vb6parse)
↓
Walk the CST tree recursively
(emit_token for each token, emit_verbatim for designer nodes)
↓
For each token, run passes in order:
➊
LineEndingPass
— detect & normalize CRLF/LF
➋
CompilerDirectivePass
— #If/#Else blank line handling
➌
KeywordCasePass
— normalize keyword casing
➍
LayoutPass
— indentation & whitespace
➎
TopLevelSpacingPass
— blank lines between declarations
➏
DeduplicateBlankLinesPass
— collapse consecutive blank lines
↓
Formatted Output (String)

Why This Order Matters

The pass order is deliberate. Line ending detection must come first so all other passes can assume a consistent line ending style. Compiler directives and keyword casing can happen in either order since they operate on different tokens. Layout must come before top-level spacing, because top-level spacing needs to know where lines start. Blank line deduplication runs last, collapsing any blank lines that earlier passes may have inserted.

The FormatPass Trait

Every pass implements the FormatPass trait, which provides three hook methods called during the CST traversal. Each method has a default empty implementation, so a pass only overrides what it needs: 

pub trait FormatPass {
    fn on_node_enter(&self, _node: &CstNode, _context: &mut Context) {}

    fn on_node_exit(&self, _node: &CstNode, _context: &mut Context) {}

    fn on_token(&self, _token: &CstNode, _context: &mut Context, _buffer: &mut TokenBuffer) {}
}

Hooks Explained

on_node_enter

Called when the tree walker descends into a node, before processing its children. Used for one-time initialization (e.g., detecting line endings) and entering stateful scopes (e.g., incrementing compiler directive nesting depth).

on_node_exit

Called after all children of a node have been processed. Used for cleanup, such as decrementing a depth counter or signaling that a directive block has ended.

on_token

Called for every token in the CST. This is where the actual formatting mutations happen. The pass receives a TokenBuffer and can modify three fields: 

pub struct TokenBuffer {
    pub prefix: String,   // prepended to the emitted output
    pub text: String,     // the main token text (can be rewritten)
    pub emit: bool,       // if false, the token is suppressed entirely
}

Design insight: Using prefix for indentation and blank lines keeps token text and formatting whitespace separate. This makes it easy to reason about what the token represents versus how it should be formatted.

PassManager Orchestration

PassManager owns the vector of boxed FormatPass trait objects and iterates them in order during the CST walk. It provides three methods that mirror the trait hooks: 

pub struct PassManager<'a> {
    passes: Vec<Box<dyn FormatPass + 'a>>,
}

impl PassManager {
    pub fn on_node_enter(&self, node: &CstNode, context: &mut Context) {
        for pass in &self.passes {
            pass.on_node_enter(node, context);
        }
    }

    pub fn on_node_exit(&self, node: &CstNode, context: &mut Context) {
        for pass in &self.passes {
            pass.on_node_exit(node, context);
        }
    }

    pub fn on_token(&self, token: &CstNode, context: &mut Context) -> TokenBuffer {
        let mut buffer = TokenBuffer::from_token(token);
        for pass in &self.passes {
            pass.on_token(token, context, &mut buffer);
        }
        buffer
    }
}

The on_token method is where pass composition happens. Each pass receives the same TokenBuffer in sequence, so modifications stack:

  • LineEndingPass sets buffer.text to the detected line ending
  • KeywordCasePass rewrites buffer.text to the canonical casing
  • LayoutPass sets buffer.prefix to the indent string
  • TopLevelSpacingPass prepends an extra newline to buffer.prefix
  • All passes can suppress tokens via buffer.emit = false

Pass 1: LineEndingPass

VB6 source files may use either \r\n (CRLF) or \n (LF) line endings. The formatter detects the source file's style and normalizes all newlines to match, preserving the original convention.

Implementation

LineEndingPass is a singleton pass — it runs its detection logic exactly once using a Cell<bool> guard: 

pub struct LineEndingPass {
    initialized: Cell<bool>,
}

impl FormatPass for LineEndingPass {
    fn on_node_enter(&self, node: &CstNode, context: &mut Context) {
        if self.initialized.replace(true) { return; }
        
        // Detect line ending from root node text
        if node.text().contains("\r\n") {
            context.line_ending = LineEnding::Crlf;
        } else {
            context.line_ending = LineEnding::Lf;
        }
        
        // First token needs indentation since it's the start of the file
        context.pending_indent = true;
    }

    fn on_token(&self, token: &CstNode, context: &mut Context, buffer: &mut TokenBuffer) {
        if token.kind() == SyntaxKind::Newline {
            // Normalize to detected line ending style
            buffer.text = context.line_ending.to_string();
            buffer.emit = true;
        }
    }
}

Shared State Management

The pass sets two context flags during its one-time initialization:

  • context.line_ending — used by all subsequent passes when emitting newlines
  • context.pending_indent — signals that the first token needs indentation (always true at file start)

Pass 2: CompilerDirectivePass

VB6 compiler directives (#If, #ElseIf, #Else, #End If) are a unique challenge. They can be nested, they affect indentation of enclosed code blocks, and users may want blank lines around or inside directive blocks.

State Tracking

The pass tracks two pieces of state via Context: 

// In Context:
pub directive_phase: Option<DirectivePhase>  // BeforeDirective | BeforeBody | AfterDirective
pub compiler_directive_depth: usize          // nesting depth of #If blocks

Blank Line Logic

The pass handles two independent formatting options:

blank_lines_around_directives (default: false)
  • Inserts a blank line before #If and after #End If
  • Uses pending_blank flag and directive_phase to track positioning
blank_lines_inside_directives (default: false)
  • Inserts a blank line between the directive block and the code it encloses
  • Triggers when entering a StatementList inside a CompilerDirective node

Nesting Depth

Nested directives like #If A Then #If B Then ... #End If #End If are handled by incrementing compiler_directive_depth on on_node_enter for CompilerDirective nodes and decrementing on on_node_exit. The depth is used to compute correct indentation for directive keywords.

Pass 3: KeywordCasePass

VB6 has a rich set of keywords, and teams may prefer different casing styles: SUB, sub, Sub, or sub. The pass normalizes all keywords to the configured style.

Canonical Keyword Extraction

VB6Parse's SyntaxKind enum uses a camelCase naming convention for keyword variants (e.g., SubKeyword, EndIfKeyword, ForEachKeyword). The pass strips the Keyword suffix to get the canonical text: 

// SyntaxKind::SubKeyword -> "Sub"
// SyntaxKind::EndIfKeyword -> "EndIf"
// SyntaxKind::ForEachKeyword -> "ForEach"

fn keyword_camel_text(kind: SyntaxKind) -> Option<&str> {
    let name = std::any::type_name_of_val(&kind);
    name.strip_suffix("Keyword")
}

Casing Styles

Four transformation modes are supported:

Style Sub End If For Each
"upper" SUB END IF FOR EACH
"lower" sub end if for each
"camel" (default) Sub End If For Each
"first" Sub End if For each

Design note: Compound keywords like End If are represented as two separate tokens in the CST (End + If). The pass applies the casing transformation to each token independently, which means "camel" produces End If while "first" produces End if.

Pass 4: LayoutPass

LayoutPass is the most complex pass, responsible for indentation (spaces) and whitespace normalization. It processes every token kind differently.

Token-Kind Dispatch

The pass matches on SyntaxKind and applies different logic per token type: 

impl FormatPass for LayoutPass {
    fn on_token(&self, token: &CstNode, context: &mut Context, buffer: &mut TokenBuffer) {
        match token.kind() {
            SyntaxKind::Whitespace => {
                if context.pending_indent {
                    // Suppress original whitespace — we'll generate it
                    buffer.emit = false;
                } else {
                    // Collapse all whitespace to a single space
                    buffer.text = " ".to_string();
                }
            }
            SyntaxKind::Newline => {
                // Handled by LineEndingPass — no action needed
            }
            SyntaxKind::EndOfLineComment | SyntaxKind::RemComment => {
                if context.pending_indent {
                    buffer.prefix = " ".repeat(context.indent_level * self.settings.indent_size);
                }
                context.pending_indent = false;
                context.line_has_content = true;
            }
            _ => {
                // Any content token — generate indent if needed
                if context.pending_indent {
                    buffer.prefix = " ".repeat(context.indent_level * self.settings.indent_size);
                }
                context.pending_indent = false;
                context.line_has_content = true;
            }
        }
    }
}

Indentation Model

Indentation is managed by incrementing context.indent_level when entering a StatementList node in the CST walker and decrementing on exit. This covers:

  • Sub / Function / Property procedure bodies
  • If / ElseIf / Else branches
  • For / Do / While loop bodies
  • With blocks
  • Select Case / Case branches
  • Type / Enum blocks

Whitespace Normalization

Original whitespace (indentation spaces) is suppressed when pending_indent is true (i.e., at the start of a new line), because the pass generates fresh indentation. Between tokens on the same line, all sequences of whitespace are collapsed to a single space.

Pass 5: TopLevelSpacingPass

This pass inserts blank lines between top-level declarations — between procedures, between Declare blocks, and between Option statements. It avoids blank lines between consecutive declarations of the same kind (e.g., two Private Sub procedures in a row).

Top-Level Category Classification

Declarations are classified into three categories: 

enum TopLevelCategory {
    Option,    // Option Explicit, Option Compare, Option Base
    Declare,   // Public Declare, Private Declare, Friend Declare
    Other,     // Sub, Function, Property, Event, Enum, Type
}

The classification scans the raw source text of each top-level block, checking the first significant word. Declarations with visibility modifiers (e.g., Private Declare, Friend Sub) are handled by checking both the modifier and the primary keyword.

Comment Attachment

A subtle but important case: comments preceding a declaration are treated as part of that declaration's block. A blank line is inserted before the declaration, not before the comment. This preserves the natural flow: 

' This procedure does something important
Sub Bar()            ' ← blank line inserted before this line
    ...
End Sub

Insertion Logic

On first on_node_enter, the pass parses the full source text and builds a sorted set of line numbers where blank lines should be inserted. Subsequent tokens at the start of a line check whether their line number is in this set: 

fn on_token(&self, ... buffer: &mut TokenBuffer) {
    if self.should_insert_blank_line(token, context) {
        buffer.prefix.push('\n');  // Extra newline before the token
    }
}

Category Rules

Blank lines are inserted between two declarations unless both have the same category:

Blank line inserted
  • Option → Declare
  • Declare → Sub
  • Sub → Enum
  • Enum → Option
No blank line
  • Sub → Sub (same category)
  • Option → Option (same category)
  • Declare → Declare (same category)

Pass 6: DeduplicateBlankLinesPass

The final pass is a safety net. Earlier passes (especially CompilerDirectivePass and TopLevelSpacingPass) may insert blank lines, and in edge cases multiple blank lines could accumulate. This pass collapses consecutive newlines to at most two (one blank line).

Implementation

The pass tracks a Cell<usize> counter of consecutive newlines and processes both buffer.prefix and buffer.text: 

pub struct DeduplicateBlankLinesPass {
    newline_streak: Cell<usize>,
}

impl FormatPass for DeduplicateBlankLinesPass {
    fn on_token(&self, ... buffer: &mut TokenBuffer) {
        buffer.prefix = self.sanitize_chunk(&buffer.prefix);
        buffer.text = self.sanitize_chunk(&buffer.text);
    }
}

fn sanitize_chunk(&self, input: &str) -> String {
    let mut result = String::new();
    let mut streak = 0usize;
    
    for ch in input.chars() {
        if ch == '\n' {
            if streak < 2 {
                result.push(ch);
            }
            streak += 1;
        } else {
            streak = 0;
            result.push(ch);
        }
    }
    result
}

Why run this last? Because it operates character-by-character on the output buffer, running it after all other passes ensures it deduplicates blank lines produced by the entire pipeline, not just original blank lines in the source.

CST Walk & Emission

CstFormatter owns the tree walk that drives all passes. It recursively walks the CST produced by vb6parse, dispatching each node to the appropriate handler: 

struct CstFormatter<'a> {
    cst: ConcreteSyntaxTree,
    output: String,
    context: Context,
    passes: PassManager<'a>,
}

impl CstFormatter {
    fn walk_node(&mut self, node: &CstNode) {
        // 1. Tokens are emitted directly
        if node.is_token() {
            self.emit_token(node);
            return;
        }

        // 2. Designer nodes are emitted verbatim (skip formatting)
        if is_designer_node(node.kind()) {
            self.emit_verbatim(node);
            return;
        }

        // 3. Run on_node_enter hooks on all passes
        self.passes.on_node_enter(node, &mut self.context);

        // 4. Walk children — increment indent for StatementList nodes
        match node.kind() {
            SyntaxKind::StatementList => {
                self.context.indent_level += 1;
                for child in node.children() {
                    self.walk_node(child);
                }
                self.context.indent_level = self.context.indent_level.saturating_sub(1);
            }
            _ => {
                for child in node.children() {
                    self.walk_node(child);
                }
            }
        }

        // 5. Run on_node_exit hooks on all passes
        self.passes.on_node_exit(node, &mut self.context);
    }

    fn emit_token(&mut self, token: &CstNode) {
        let buffer = self.passes.on_token(token, &mut self.context);
        if buffer.emit {
            self.output.push_str(&buffer.prefix);
            self.output.push_str(&buffer.text);
        }
    }
}

Pre-allocated Output Buffer

The output String is pre-allocated to the size of the original source text, which avoids reallocations in the common case where formatting doesn't dramatically change file size: 

let root = cst.to_root_node();
let output = String::with_capacity(root.text().len());

Designer Block Preservation

VB6 .frm, .cls, and .ctl files contain a designer block — a BEGIN ... END structure that describes form control geometry (position, size, properties). This block is written and rewritten by the VB6 IDE, and any modification to it will be lost on the next IDE save or risk corrupting the form layout.

CstFormatter detects designer nodes by their SyntaxKind and emits them verbatim, bypassing the entire pass pipeline: 

fn is_designer_node(kind: SyntaxKind) -> bool {
    matches!(kind, SyntaxKind::VersionStatement | SyntaxKind::PropertiesBlock)
}

fn emit_verbatim(&mut self, node: &CstNode) {
    let text = node.text();
    let ends_line = text.ends_with('\n');
    self.output.push_str(text);
    
    // Update context so formatting after the block is correct
    self.context.pending_indent = ends_line;
    self.context.line_has_content = !ends_line;
    self.context.last_was_blank = false;
}

This is why a multi-pass approach was essential: a line-based formatter would need complex exception handling to skip designer blocks. By using a CST, designer blocks are first-class nodes that can be identified and skipped structurally. The pass pipeline then processes only the code section, which is where formatting rules apply.

Pass Composition

The power of the multi-pass design lies in how passes compose. Each pass operates independently on the shared TokenBuffer and Context, and their effects combine naturally:

Example: Formatting a single indented token 
    Dim x As Integer    ' Original source

Token stream: Whitespace(" ") → DimKeyword → Whitespace(" ") → DimIdentifier → ...

Processing through the pipeline:

  1. LineEndingPass — no-op for non-newline tokens
  2. CompilerDirectivePass — no-op (not a directive token)
  3. KeywordCasePass — rewrites Dim to match keyword_case setting
  4. LayoutPass — suppresses original Whitespace(" ") (because pending_indent is true), then sets buffer.prefix = " " (4 spaces for indent_level 1)
  5. TopLevelSpacingPass — no-op (not a top-level declaration at this point)
  6. DeduplicateBlankLinesPass — no-op (no consecutive newlines)

Result: buffer.prefix = " " + buffer.text = "Dim" → " Dim"

Pass Independence

Because each pass only reads Context state and writes to TokenBuffer, passes can be reordered or removed without breaking others. For example:

  • Removing KeywordCasePass leaves all other formatting intact
  • Reordering CompilerDirectivePass and KeywordCasePass has no effect
  • Removing DeduplicateBlankLinesPass would allow multiple blank lines to persist in edge cases

Idempotency Guarantee

A fundamental invariant of the formatter is idempotency: formatting a file twice produces the same output as formatting it once: 

format(source) == format(format(source))

This is guaranteed by design:

  • LayoutPass always generates the same indentation regardless of the input spacing
  • KeywordCasePass always produces the same casing for each keyword
  • LineEndingPass normalizes to the detected style, which is the same on the second pass
  • DeduplicateBlankLinesPass ensures no more than one blank line exists
  • TopLevelSpacingPass produces the same insertion set each time (it classifies top-level categories from the formatted text, which is stable)

Every test case asserts this invariant: 

let formatted_once = fmt_source(source, &settings).unwrap();
let formatted_twice = fmt_source(&formatted_once, &settings).unwrap();
assert_eq!(formatted_once, formatted_twice);

Future Considerations

The multi-pass architecture is well-positioned for future extensions:

1. Linting Passes

Additional passes could detect style violations (e.g., missing Option Explicit, unused variables, naming convention violations) without modifying the output. These would report errors through Context rather than modifying TokenBuffer.

Trade-off: Would require a new pass variant (e.g., LintPass) with different output semantics — collect errors instead of modifying tokens.

2. Trivia Passing

Currently, comments and whitespace are preserved in the CST but the passes don't perform sophisticated trivia handling (e.g., reflowing comments, moving trailing comments to leading comments). A dedicated trivia pass could handle these cases.

Trade-off: More complexity in the layout pass or a new pass, but richer comment-aware formatting.

3. Extensibility

The pass could be made configurable at runtime, allowing users to add custom passes via a plugin system. This would enable team-specific formatting rules without modifying the formatter core.

Trade-off: Would require an unstable plugin API and more complex pass registration. Could be deferred until there's demand.

Complexity Analysis

The pipeline has the following time and space characteristics:

Complexity Value Explanation
Time O(n) 6 passes × n tokens = constant factor × linear
Space (output) O(n) Output buffer sized to input
Space (context) O(depth) Recursion depth of CST walk
Space (TopLevelSpacing) O(n) Stores set of insertion line numbers

Key insight: The constant factor of 6 passes is negligible compared to the cost of CST construction in vb6parse. The formatter is typically 5-10× faster than the parser, making the multi-pass overhead imperceptible in practice.

Summary

vb6format's multi-pass formatting pipeline is a pragmatic design that separates formatting concerns into six focused, independently testable passes. The shared Context and TokenBuffer allow passes to compose their modifications naturally, while the CST structure provides the semantic context needed for VB6-specific challenges like designer block preservation, compiler directive handling, and compound keyword casing.

  1. LineEndingPass — normalizes line endings to match the source file
  2. CompilerDirectivePass — manages blank lines around and inside #If blocks
  3. KeywordCasePass — normalizes keyword casing to a configured style
  4. LayoutPass — handles indentation and whitespace normalization
  5. TopLevelSpacingPass — inserts blank lines between top-level declarations
  6. DeduplicateBlankLinesPass — collapses consecutive blank lines

Why multi-pass was chosen because:

  • ✅ Each formatting concern is independent and has different triggering conditions
  • ✅ VB6's unique features (directives, designer blocks, compound keywords) require specialized handling
  • ✅ Individual passes are easier to test and reason about than a monolithic formatter
  • ✅ Pass composition is clean — each pass modifies TokenBuffer independently
  • ✅ The pipeline is idempotent by design — every pass produces stable output
  • ✅ Extensions (linting, custom rules) can be added as new passes without modifying existing ones

This architecture successfully handles the diverse formatting requirements of VB6 source code — from hybrid .frm files with opaque designer blocks to deeply nested compiler directives — while maintaining a clean, extensible, and performant implementation.
