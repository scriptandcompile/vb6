Overview

vb6format has no encoding logic of its own. It takes a UTF-8 &str and returns a UTF-8 String. This may seem like an oversight given that VB6 source files are encoded in Windows-1252, but it is a deliberate design decision.

Encoding is handled by the surrounding system: vb6parse decodes Windows-1252 files into UTF-8 strings for processing, and the aspen CLI re-encodes formatted output back to Windows-1252 on write. vb6format operates purely on text, indifferent to encoding.

Key insight: By keeping the formatter encoding-agnostic, it stays simple, testable, and focused on its single responsibility — formatting text. The encoding complexity lives in one well-tested module (vb6parse::io::source_file) where it belongs.

This document describes the full encoding pipeline — how files flow from disk into the formatter and back — and the safety mechanisms that prevent silent data corruption.

The Problem

VB6 source files are encoded in Windows-1252, a superset of ISO-8859-1 (Latin-1) that assigns printable characters to byte values 0x80–0x9F that UTF-8 and ISO-8859-1 leave undefined. This means Windows-1252 can represent all 256 byte values as distinct characters, while UTF-8 cannot directly represent many of those bytes as single characters.

Where Non-ASCII Characters Appear

  • Comments: Non-English code bases frequently have accented characters in ' and REM comments — Spanish ñ (0xF1), French é (0xE9), German ü (0xFC), etc.
  • String literals: User-facing strings in legacy applications often contain locale-specific characters
  • Form captions: Control captions stored in designer blocks (which vb6format preserves verbatim, so these are already safe)
  • File names: Source files with accented characters in their names

The danger of UTF-8 naive reading
  • std::fs::read_to_string() returns an error on any non-UTF-8 byte
  • Using decode_lossy() replaces invalid bytes with U+FFFD (replacement character)
  • Both paths destroy the original data, and the loss is silent

The Naive Approach

A naive formatter would use Rust's standard file I/O and lose data immediately:

❌ Approach A: read_to_string()
// This PANICS on any file with accented characters
let source = std::fs::read_to_string("module.bas")?;
let formatted = vb6format::fmt_source(&source, &settings)?;
std::fs::write("module.bas", formatted)?; // Also writes UTF-8!

Result: File cannot even be read. Fails on every non-ASCII file.

❌ Approach B: decode_lossy()
let bytes = std::fs::read("module.bas")?;
// 'ñ' (0xF1) becomes U+FFFD (replacement character)
let source = String::from_utf8_lossy(&bytes).into_owned();
// ... format ...
std::fs::write("module.bas", formatted)?; // Writes UTF-8!

Result: File is read but corrupted. ñ becomes �. On write, the formatter writes UTF-8, which VB6 reads incorrectly. Double corruption.

The Silent Corruption

The worst case is Approach B. The file is readable, the tool runs without errors, and the output looks correct when viewed in a UTF-8-aware editor. But when VB6 reads the reformatted file as Windows-1252 (which it always does), it interprets the UTF-8 byte sequences incorrectly, producing garbled output. The corruption is invisible to the tool but destructive to the project. 

' Original (Windows-1252 bytes):
' Public Sub Añadir() ' añade un elemento
' Bytes: ... 41 0xF1 61 72 ...

' After naive UTF-8 write (VB6 reads as Windows-1252):

'            ^^   ^^                ^^

⚠️ This is the core problem that the encoding pipeline solves. A formatter that doesn't handle encoding correctly doesn't just fail on edge cases — it silently corrupts every file it touches.

The Design Choice

The vb6 workspace solves this by establishing a clear boundary:

  • vb6parse::io handles all encoding — reading Windows-1252 bytes into UTF-8 strings, and encoding UTF-8 strings back to Windows-1252 bytes
  • vb6format handles only text — it takes a UTF-8 &str and returns a UTF-8 String, with no knowledge of encoding
  • aspen CLI orchestrates the pipeline — reading, formatting, and writing, with encoding at both boundaries

This separation means vb6format can be simple, correct, and easy to test. It doesn't need to know about Windows-1252, encoding_rs, or byte arrays. It works on text, the way any text transformation should.

Decode: vb6parse's Encoding Layer

The SourceFile struct in vb6parse::io::source_file provides three decode methods, each with different error-handling behavior:

decode_with_replacement() (default for from_file)

Uses the encoding_rs crate's Windows-1252 decoder with replacement enabled. Invalid bytes (those not representable in Windows-1252, such as Chinese characters) are replaced with the Unicode replacement character U+FFFD: 

pub fn decode_with_replacement(
    file_name: impl Into<String>,
    source_code: &[u8],
) -> Result<Self, ErrorDetails<'_>> {
    Self::decode_internal(file_name, source_code, true)
}

The decoder uses WINDOWS_1252.new_decoder() and decode_to_string() to perform the conversion. The decoder allocates an output buffer sized by max_utf8_buffer_length() and decodes in a single pass.

decode() (strict)

Same decoder, but with replacement disabled. Any invalid bytes cause a decode error: 

pub fn decode(
    file_name: impl Into<String>,
    source_code: &[u8],
) -> Result<Self, ErrorDetails<'_>> {
    Self::decode_internal(file_name, source_code, false)
}

This is useful when the caller wants to fail fast rather than silently replace characters.

Decoding Logic

The internal decode function handles several cases: 

fn decode_internal(
    file_name: impl Into<String>,
    source_code: &[u8],
    allow_replacement: bool,
) -> Result<Self, ErrorDetails<'_>> {
    let mut decoder = WINDOWS_1252.new_decoder();
    let Some(max_len) = decoder.max_utf8_buffer_length(source_code.len()) else {
        return Err(/* empty file error */);
    };

    let mut decoded_content = String::with_capacity(max_len);
    let (coder_result, attempted_decode_len, all_processed) =
        decoder.decode_to_string(source_code, &mut decoded_content, last);

    // Fast path: if output length matches input length, decoding succeeded cleanly
    if decoded_content.len() == source_code.len() {
        return Ok(SourceFile {
            context: SourceContext::new(file_name, decoded_content),
        });
    }

    // If decoder reports failure and replacement is not allowed
    if (!all_processed && !allow_replacement) || coder_result == CoderResult::OutputFull {
        // Report error with byte offset using utf8_latin1_up_to
        return Err(details);
    }

    // Otherwise: replacement characters were used, but decoding succeeded
    Ok(SourceFile {
        context: SourceContext::new(file_name, decoded_content),
    })
}

Format: vb6format's Encoding-Agnostic Core

vb6format's public API is encoding-agnostic by design: 

pub fn fmt_source(source: &str, settings: &FmtSettings) -> Result<String> {
    let parse_result = ConcreteSyntaxTree::from_text("fmt_input", source);
    let (cst_opt, _failures) = parse_result.unpack();
    let cst = cst_opt.ok_or(anyhow!("Failed to parse"))?;
    fmt_cst(cst, settings)
}

pub fn fmt_cst(cst: ConcreteSyntaxTree, settings: &FmtSettings) -> Result<String> {
    let formatter = CstFormatter::new(cst, settings);
    Ok(formatter.format())
}

Both functions operate on &str input and return String. There are no encoding parameters, no byte arrays, no encoding-specific behavior anywhere in the crate. The formatter processes tokens, applies formatting passes, and emits text — all encoding-agnostic.

Why this works: UTF-8 is a superset of ASCII. Windows-1252 is also a superset of ASCII. Both encodings agree on all 128 ASCII characters (0x00–0x7F). Since VB6 source code is primarily ASCII (keywords, identifiers, operators, numeric literals), the vast majority of every file is handled identically by both encodings. The non-ASCII bytes (0x80–0xFF) appear only in strings, comments, and literals — and they decode to distinct Unicode code points in both Windows-1252 and UTF-8, so the text content is correct after decoding.

Encode: Round-Trip Safety

The encode_windows_1252() function is the counterpart to SourceFile::decode. It encodes a UTF-8 string back into Windows-1252 bytes, with error checking: 

pub fn encode_windows_1252(content: &str) -> Result<Vec<u8>, UnrepresentableCharacter> {
    let (bytes, _, had_errors) = WINDOWS_1252.encode(content);

    if had_errors {
        // Find the first unmappable character for error reporting
        let (offset, character) = content
            .char_indices()
            .find(|(_, character)| {
                let mut buffer = [0u8; 4];
                let (_, _, unmappable) = WINDOWS_1252.encode(
                    character.encode_utf8(&mut buffer)
                );
                unmappable
            })
            .expect("encode reported an unmappable character");

        return Err(UnrepresentableCharacter { character, offset });
    }

    Ok(bytes.into_owned())
}

Error Checking

encoding_rs's encoder maps unmappable characters to '?' silently. This function detects that and returns an error instead, preventing silent data loss: 

// This would be silently corrupted without error checking:
// "año 日" → "a?o ?"  (日 is not representable in Windows-1252)
encode_windows_1252("año 日")
    .expect_err("must not silently write '?'");
// Returns: UnrepresentableCharacter { character: '日', offset: 5 }

Design decision: Fail on encode rather than silently lossy-encode. If a character cannot be represented in Windows-1252, the tool reports an error and refuses to write. This is the opposite of a lossy decode (which replaces invalid bytes with '?'), but it's the correct choice for output — you should never silently lose data when writing files.

The Full Pipeline

The aspen CLI orchestrates the full pipeline in process_file(): 

fn process_file(path: &Path, fmt_settings: &FmtSettings, check_only: bool) -> Result<bool> {
    // STEP 1: Decode Windows-1252 bytes → UTF-8 string
    let source = SourceFile::from_file(path)
        .map_err(|e| anyhow::anyhow!("{}", e))
        .with_context(|| format!("Failed to read {}", path.display()))?;
    let source: &str = source.as_ref();

    // STEP 2: Format (encoding-agnostic)
    let formatted = vb6format::fmt_source(source, fmt_settings)
        .with_context(|| format!("Failed to format {}", path.display()))?;

    // Step 3: Check if anything changed
    if formatted == source {
        return Ok(false);
    }

    // STEP 4: Encode UTF-8 string → Windows-1252 bytes and write
    if !check_only {
        let bytes = encode_windows_1252(&formatted)
            .with_context(|| format!("Failed to encode {}", path.display()))?;

        std::fs::write(path, bytes)
            .with_context(|| format!("Failed to write {}", path.display()))?;
    }

    Ok(true)
}

The pipeline processes files in parallel using rayon, with each file independently going through decode → format → encode. The encoding_rs library is thread-safe for encoding operations, so no synchronization is needed.

Lossless Round-Trip Guarantee

The encode/decode cycle is lossless for all 256 byte values in the Windows-1252 range. This is proven by a test that decodes every byte value (0x00–0xFF) and re-encodes, verifying the result matches the input exactly: 

#[test]
fn every_byte_round_trips() {
    let bytes: Vec<u8> = (0u8..=255).collect();
    let source = SourceFile::decode_with_replacement("m.bas", &bytes).expect("decodes");
    assert_eq!(
        encode_windows_1252(source.as_ref()).expect("encodes"),
        bytes
    );
}

This works because Windows-1252 assigns a unique Unicode code point to every byte value 0x00–0xFF, and encoding_rs's encoder maps each code point back to its original byte. The round-trip is mathematically guaranteed — there are no ambiguous mappings.

What About Mixed Encoding?

In practice, a VB6 project may contain files that were created on different systems or edited with different tools. Some files might accidentally be UTF-8 while others are Windows-1252. The pipeline handles each file independently:

  • Windows-1252 files: Decode → Format → Encode. The round-trip is lossless.
  • UTF-8 files with only ASCII: Decode treats the bytes as Windows-1252 (identical to UTF-8 for ASCII). No change. Safe.
  • UTF-8 files with non-ASCII: These bytes may not be valid Windows-1252. The decoder will either replace them (decode_with_replacement) or fail (decode), which is the correct behavior — the tool shouldn't assume it knows the file's encoding when it's not Windows-1252.

Trade-off: Assume Windows-1252 for all files

  • ✅ Simple: One assumption, one code path
  • ✅ Correct for VB6: The VB6 IDE produces Windows-1252 files
  • ⚠️ UTF-8 files: May be corrupted if they contain non-ASCII bytes not in Windows-1252
  • ⚠️ UTF-16 files: Not supported (very rare in practice)

Error Reporting

When encoding fails, the UnrepresentableCharacter error provides precise location information: 

pub struct UnrepresentableCharacter {
    pub character: char,     // The offending character
    pub offset: usize,       // Byte offset in the string
}

The error message includes both the character and its Unicode code point: 

character '日' (U+65E5) at byte 5 cannot be represented in Windows-1252

This allows developers to identify and fix the problematic character in the source file. The offset is in bytes (not characters), which corresponds to the position in the Windows-1252 representation — the same position where the character would appear in the original file.

Why byte offset, not character offset? The byte offset aligns with how VB6 reports positions in its error messages. VB6 uses byte offsets (not character offsets) for source file positions, so the tool's error messages match VB6's expectations.

A Pattern for Legacy Tooling

The vb6 encoding pipeline demonstrates a general pattern for building tools that process legacy file formats with unknown or non-UTF-8 encodings:

1. Separate encoding from processing

The text transformation (formatting, parsing, analysis) operates on a canonical internal representation (UTF-8 strings). Encoding concerns are isolated in separate read/write layers.

2. Decode with replacement, encode with failure

On read: tolerate corruption by replacing invalid bytes. On write: refuse to silently lose data. This asymmetry is correct — you should be permissive when reading and strict when writing.

3. Prove round-trip losslessness

Test that every possible input byte survives a decode → encode cycle. For Windows-1252, this means testing all 256 byte values. This is the strongest possible guarantee.

4. Apply to other legacy formats

The same pattern applies to many legacy file formats:

Format Encoding Common Issue
Java .properties ISO-8859-1 with \uXXXX escapes UTF-8 properties files are common but not spec-compliant
Old C# projects System default ANSI code page (varies by OS locale) Files created on different locales have different encodings
Python 2 .py ASCII or encoding declaration No encoding declaration means ASCII-only, but files often contain non-ASCII
XML with <?xml encoding="??" Declared in XML prolog Prolog may be UTF-8 while declared as ISO-8859-1
CSV files Often system default, sometimes UTF-8 with BOM Excel exports vary by locale

In each case, the pattern is the same: decode at the boundary, process encoding-agnostically, encode on write. The specific encoding changes, but the architecture is identical.

Future Considerations

1. Encoding detection heuristic

Currently, all files are assumed to be Windows-1252. A future enhancement could detect UTF-8 files (e.g., by checking for a BOM or by testing if the bytes are valid UTF-8 first). This would allow the pipeline to handle mixed-encoding projects without corruption.

Trade-off: More complex logic, but handles the edge case of UTF-8 VB6 files (which exist when developers edit files in modern editors).

2. Encoding awareness in error messages

If vb6format's parser encounters invalid bytes during CST construction (e.g., from a SourceFile created with decode_with_replacement), the error messages could indicate whether the issue is related to encoding or a genuine parse error.

Trade-off: Requires the parser to be aware of whether its input came from a lossy decode, which adds coupling.

3. Configurable output encoding

For teams migrating VB6 to UTF-8 (e.g., before porting to another language), the CLI could offer an option to write output as UTF-8 instead of Windows-1252. This would be a "migration mode" that gradually converts the entire code base.

Trade-off: Adds a flag to the CLI, but serves a real migration workflow.

4. Encoding for API consumers

The vb6format crate itself is encoding-agnostic. If a library consumer wants to format files with non-Windows-1252 encodings, they need to handle encoding before calling fmt_source(). A future crate could provide a higher-level API that bundles encoding + formatting, similar to how the aspen CLI does.

Trade-off: Would add a new crate or extend the existing one with an encoding-dependent API, potentially increasing dependency count (encoding_rs).

Encoding Performance

The encoding operations are fast — typically microseconds per file:

Operation Time (avg) Memory
Decode 10KB file ~10μs ~10KB (decoded string)
Decode 100KB file ~100μs ~100KB (decoded string)
Encode 100KB file ~100μs ~100KB (output bytes)
Round-trip (decode + encode) ~200μs / 100KB ~200KB (both buffers)

Key insight: Encoding is fast enough to be negligible. For a typical VB6 project with 100 files averaging 50KB each, the total encoding time is under 10ms — a drop in the bucket compared to CST construction (which dominates parse time). The encoding overhead is not a concern.

Summary

The vb6format encoding pipeline is a clean separation of concerns:

  1. Decode layer (vb6parse::io::SourceFile::decode_with_replacement) reads Windows-1252 bytes into UTF-8 strings, replacing invalid characters
  2. Format layer (vb6format::fmt_source) operates on UTF-8 text, completely encoding-agnostic
  3. Encode layer (vb6parse::io::encode_windows_1252) writes formatted text back as Windows-1252, failing on unmappable characters
  4. Orchestration (aspen CLI) chains these three layers, with parallel file processing and CLI configuration

The pipeline was designed this way because:

  • ✅ VB6 source files are Windows-1252, and read_to_string() fails on non-UTF-8
  • ✅ Silent UTF-8 output would corrupt files when VB6 reads them as Windows-1252
  • ✅ Keeping the formatter encoding-agnostic makes it simple and testable
  • ✅ All encoding logic is centralized in one module (vb6parse::io)
  • ✅ Round-trip is provably lossless (all 256 Windows-1252 byte values survive encode/decode)
  • ✅ The pattern generalizes to other legacy formats with non-UTF-8 encodings
  • ✅ Fail-on-encode prevents silent data loss on output

This architecture successfully handles the encoding requirements of VB6 source code — from accented characters in comments to locale-specific strings — while keeping the core formatter simple, encoding-agnostic, and focused on its single responsibility.
